# 深度问答

## 一、目标和入口

通过材料核对和分轮问答，使技术问题、实现过程、必要条件、作用机制、适用边界和候选保护点清楚，并据此修改交底书。可从整套方案、单个章节、特定技术点或专家意见开始；不要求每次重做全案。

基础输入可以只有交底书和术语约定。项目资料、检索原文、代码、实验记录有则读取；缺少时提出与本轮问题有关的具体缺口，不要求先交齐所有资料。

本模式允许讨论技术内容的增补和改变，但用户决定、证据状态和正文写入权限必须分开。发明构思可以尚未实际实现；不能把设想写成已经验证的事实。

## 二、与grill-with-docs配合

进入本模式时，先发现并读取目标环境中的`grill-with-docs`，再读取它引用的`grilling`和`domain-modeling`。支持技能调用工具时按环境机制加载；没有名为Skill的工具时，按已发现的真实路径读取对应SKILL.md，不虚构工具调用。不要在新环境硬编码本机绝对路径。

复用以下能力：

- grilling：把问题组织为有前提依赖的决策树；本轮只讨论前提已明确的问题；用户回答后重算下一轮问题。
- domain-modeling：澄清概念，发现同名异义或同义异名，用具体场景检验边界，记录已确认术语和重要取舍。

本技能按交底书任务明确限定其文件行为：术语写入已有的写作术语表，重要决定写入技术方案工作记录，不另外建立内容重复的CONTEXT.md或ADR目录。保留既有项目的记录形式。用户没有授权记录时只在对话整理，不自动创建文件。

grilling要求查阅环境事实时，先通过可用工具查找，不把能查到的事实当作问题丢给用户。子代理仅在当前环境与用户授权允许时使用；不能依赖子代理才能推进。

依赖技能不可用时说明缺失项，不自动安装、不声称已调用。可提出按本文件自带流程继续；用户明确要求必须使用该依赖时，等待其解决或允许替代。基础写作模式不依赖上述技能。

## 三、案件工作区约定

这是运行技能时的案件目录，不是技能安装目录。技能只存通用规则和空白模板，案件资料不写回技能。

### 建立和接入

- 先检查现有入口、文件用途及适用工作区规则。已有同职责文件就复用，不另建一份。
- 已有目录无需为了本约定自动重命名、搬迁或补建所有空目录。
- 新建案件按用户授权和实际需要逐步创建；最小可用材料为主稿，记录工作被授权后再建立术语表和工作记录。
- 公共模板和写作规范从本技能读取，不要求每个案件复制一套公共参考目录。
- 多案件保持独立；跨案资料只能在授权范围内引用并说明用途，不当成本案研发证据。

| 02_检索与对比/检索批次 | 每批目的、查询、来源、命中、阅读范围、结果和限制；必要的当时综述 | 按实际活动创建，不为每个问答回合建批次；历史认识不偷偷改写，修正写入当前对照并注明 |
| 02_检索与对比/现有技术原文 | 已获取的专利、论文、标准及原文定位 | 原件只读；同一文本不重复保存，同族或不同公开版本保留身份差异；未下载只记录链接 |
| 03_技术方案与证据/方案确认 | 当前确认方案、待解决问题、候选保护点、重要决定及正文落实状态 | 深度问答主要工作记录，具体格式见下文；不堆每轮全量草稿 |
| 03_技术方案与证据/研发与验证记录 | 既有测试条件、数据和代码入口、结果及必要验证计划 | 计划与实测结果明显区分；记录范围和限制；不能凭建议补实验结果；不导入权重、凭据或无关数据 |
| 03_技术方案与证据/附图/源文件 | 可编辑结构图、流程图及其他必要图源 | 描述已确认方案；按授权同步正文；图源可采用Mermaid或项目既有格式 |
| 03_技术方案与证据/附图/导出 | 图源生成的PNG等正式图 | 仅按要求生成；保留与图源版本的对应，图源改变不等于图片已更新 |
| 04_交底书/MD主稿 | 当前Markdown正文 | 主稿按明确授权更新，不从确认记录自动全量重写；现有其他源格式按项目约定处理 |
| 04_交底书/DOCX导出 | 用户要求生成的Word文件 | 不独立改正文；标明来源和实际导出时间；正文改变不自动刷新导出件 |
| 04_交底书/修订记录 | 版本、来源、提交和导出对应关系，检查入口 | 日常问答不逐轮写流水账；版本、导出或提交发生且授权记录时更新 |
| 04_交底书/表头信息文件 | 用户确认的名称、单位、类型、发明人和联系方式 | 沿用现有格式，可用JSON或表格；缺失不推断，表头信息不进入技术正文 |
| 05_提案与审核/第NN次提交/01_提交包 | 此次实际提交的冻结文件和必要提交说明 | 按实际次数建立，日期未知不猜；不覆盖历史提交件，也不因建目录认定已经提交 |
| 05_提案与审核/第NN次提交/02_审核意见 | 专家报告、批注原件、邮件导出或用户提供的意见摘要 | 原件只读；只有摘要时明确完整报告未取得，保留批注锚点 |
| 05_提案与审核/第NN次提交/03_意见落实 | 逐项意见、处置、理由、修改位置、复核状态 | 只在相应审核修订任务中按授权更新；用户复核与专家确认分别记录 |
| 05_提案与审核/申请凭证 | 正式申请号、受理通知等已提供凭证 | 无凭证不推断申请状态；提交评审不等于已申请 |
| 90_工具 | 实际需要的检查、绘图、导出脚本和用法 | 不为目录完整而建脚本；使用前确认作用和输出，不自动运行全部工具 |
| 99_历史版本 | 已退出使用的正式稿、旧方案和必要历史记录 | 只读追溯；当前入口明确，不把旧稿内容重新当作最新决定 |

新案件统一按提交次数组织，不同时建立另一套散放提交包和审核意见的目录。已有项目即使不一致也先映射用途，不自动迁移。检索综述放所属批次，避免另维护重复的当前分析。

## 四、技术方案工作记录

维护一份主要记录。文件顶部是当前有效认识，底部保留必要决策历史。不得只不断追加决定而让用户自行判断哪条仍有效。

### 1. 当前已确认方案

简洁说明技术问题、适用条件、整体过程、核心机制、必要条件、可选实现和相关正文位置。只写已经确认的内容；不复制完整交底书。记录当前依据的主稿版本或内容标识。

### 2. 当前待解决问题

| 字段 | 写什么 |
|---|---|
| 问题编号 | 项目内稳定的简短编号，已有编号就沿用 |
| 问题与影响 | 缺少什么，影响哪个环节或结论 |
| 前提依赖 | 需先确定哪些问题，避免提前追问 |
| 已有依据 | 文件及段落、代码或用户明确回答 |
| 下一步 | 查阅、检索、请用户决定、等待验证等具体动作 |
| 状态 | 待核对、待回答、待验证、已解决或已搁置 |

不要把每个普通措辞问题写入技术问题表。用户暂停某分支时记录范围和原因，不反复逼问。

### 3. 候选保护点

按技术问题、特征组合、作用机制、必要条件、可替换实现、文献定位、验证状态组织。复杂组合可分段，不强制使用宽表格。

每点必须区分材料记载、用户确认的设计、已有验证结果和待核验推断。用户确认设计不等于实验已完成，也不等于其区别性已经确认。

### 4. 重要决定与落实

至少记录：编号、日期、问题、确认决定、理由或真实取舍、依据、替代的旧决定、受影响章节、正文落实状态。

- 旧决定被替代时注明关系，顶部更新为现行方案；历史决定不偷偷改成新决定。
- “方案已确认”“文稿已确认”“已写入正文”分别表述。
- 未写入时记录待同步位置，不能报告正文已更新。
- 只保存影响技术方案、术语或重要写作结构的结论，不逐字保存聊天，不为每轮另建全文快照。
- 普通措辞修改不创建决策记录；无真实技术取舍不另写ADR。

## 五、问答流程

### 环节一：建立当前认识

读取主稿、术语约定和现行方案记录；有入口文件则先确认链接。输出简短的本轮范围、已有事实和关键缺口。

遇到记录与正文矛盾，先检查最新明确决定及手工修改。不要按时间戳猜测；对无法消解的冲突提出具体问题。用户仅要求讨论一个步骤时，其他范围只做必要上下文核对。

### 环节二：明确技术问题

查明具体场景、输入条件、现有做法、实际障碍和希望改善的结果。对“效果不好”“智能化不足”等宽泛说法追问发生在哪个处理环节、表现为何以及已知原因。

有相关文献则对照已有证据；尚无文献时可以先澄清问题，但不把未经核验的比较写成确定事实。不要凭本申请用了某手段就倒推对方必然存在缺陷。

### 环节三：补全实施过程

沿输入到输出检查执行者、数据组成、转换过程、接口关系、时序、计算、判断条件和异常去向。代码和材料能回答的事实先查。

发现缺口时给出明确问题及可行选项，说明哪些选项是新增建议。不要通过换用更专业的词使缺失的处理看起来完整。既有实现和拟议方案不一致时，让用户明确讨论的是哪个。

### 环节四：追问核心机制

围绕必要性和相互作用追问：

- 哪个处理直接解决前述障碍？它通过什么作用过程产生改善？
- 去掉或替换这个处理，哪些结果会改变？哪些条件使该机制成立？
- 各环节只是并列使用，还是存在数据、约束或反馈上的协同？
- 哪些是必要特征，哪些只是实现选项、工具选择或工程配置？
- 核心目的是否包含多个独立技术问题？如有，先说明关系和取舍，不自动拆案或删去内容。

模块、步骤或参数数量不能直接作为创新依据。候选保护点应体现有条件的特征组合，而不是一串功能名称。

### 环节五：检验边界和依据

用正常、失败、缺失、极端或替代实现等具体场景检查方案。场景应标为用于讨论的假设，不冒充实际测试。

检查输入条件是否足够、分支是否完整、局部检查是否被扩大为整体保证、效果是否有相应机制。分清逻辑说明、实测证据和待验证预测。

需要实验时指出最小验证问题、对照条件和应观察的结果；不强制所有发明先完成实验，也不编造结果。需要文献核验时按第七部分处理。

### 环节六：整体确认与正文修改

汇总本轮确认方案、候选核心组合、重要边界、未决问题及会影响的章节。歧义先复述理解；已有明确整体授权无需再问相同问题。

在用户确认达到共同理解后，按[写作规范](写作规范.md)生成相应完整正文。起草或写入的范围依据用户授权；仅同意技术机制时，不自动全篇落稿。

改写时联动核对问题、手段、关键点、效果、术语、图表和公式，但不因此自动修改未授权位置。写前重读实际文件，写后检查差异。

## 六、每轮提问方式

将问题视为有依赖的树，但不要求每次画图。本轮列出前提已经明确、用户可以独立回答的问题；依赖本轮答案的留到下一轮。问题很多时按可独立讨论的技术主题分轮，不为凑数量添加问题。

建议形式：

1. **当前理解**：一小段说明本轮已确定的事实和目标。
2. **关键问题**：编号提出具体问题；对方案选择给建议、理由和代价，对未知事实不编造推荐答案。
3. **影响**：指出答案将改变的机制、条件或章节。

用户的回答重新决定下一轮问题。已确认事项不反复问；有新证据推翻前提时明确说明再重开问题。新消息是对当前讨论的补充时吸收并继续，不忘记原范围。

只剩等待事实核验的分支时，可继续讨论其他独立问题。不得为了保持提问而假设尚未确认的答案。

## 七、检索、技术证据和审核意见

### 文献核对

先读检索总索引，再读当前对照，最后定位相关原文。不是每轮都联网，不以有索引就声称全文已核验。

需要新增检索时说明其针对哪个技术问题或候选区别。用户已授权检索时直接开展；用户要求必须核验的新事实按可用检索工具查询，不凭记忆写结论。遵守材料外发限制，不上传整篇未公开交底书。

记录实际查询、日期、来源、文献版本和阅读范围。每条重要比较能回到权利要求、段落或页码；只读摘要时不推广到全文。检索未找到不等于相关技术不存在。

文献目录只维护一份；重复命中补记来源；批次记录保留当时认识；新结论进入当前对照并标明依据。没有检索支持时只输出待核验的候选保护点，不作授权保证或确定法律结论。

### 技术证据

分清四类：资料已有事实、用户确认的设计、可定位的验证结果、尚待确认或验证的假设。来源口述可以记录为口述，不能自动改称实验数据。

对外效果描述遵循写作规范，内部工作记录保留未决问题。缺口不因语言变确定而消失。

### 专家意见

- 表述和结构问题转入规范润色。
- 实施缺口进入本模式追问。
- 文献和效果依据问题核对证据。
- 方案取舍说明选择及其影响，由用户决定。

意见落实表记录意见原文或忠实摘要、锚点、处置、理由、修改位置和状态。待处理、修改中、已修改待复核、已复核与专家已确认不能混用。部分采纳或不采纳写原因；不因专家提出就直接改写方案。

## 八、授权、持久记录和状态

- “深度问答”可以只在对话进行。“深度问答并记录”授权在指定案件中持续维护技术方案工作记录和写作术语表；已有同职责文件优先复用。这不等于授权修改主稿、目录结构、图示或全部索引。
- 用户已明确要求建立新案件工作区时，按实际需要创建导航和相关目录，不逐个空文件请求批准。只有要求讨论时不建目录。
- 有记录授权后，每轮收敛的决定和术语及时写入；未决问题保留在待解决部分，不当作已确认方案。记录文件更新不自动触发正文同步。
- 用户授权按确认结果直接修改正文时，完成范围内的关联修改，不再反复索要同一许可；写后报告事实。
- 检索记录、审核落实、版本索引按各自任务授权更新，不因为处于深度问答就维护所有文件。
- 原件、冻结提交件和历史稿只读；重命名、迁移、升版、导出、Git提交推送和对外发送不自动触发。
- 状态变化以实际用户决定、交付行为或凭证为依据。创建文件夹、收到审核意见或修改完主稿都不能自动变更为已提案或已申请。

## 九、继续工作与结束

继续工作按“当前入口→技术方案工作记录→术语表→相关正文→必要来源”恢复。先检查哪些决定尚未写入正文、哪些候选点仍待核验。无需重读全部聊天、历史稿和批次综述。

本轮可以在以下状态结束：

- 范围内关键依赖明确并完成整体确认，进入起草或交付；
- 已列明仍缺什么、影响哪里和下一步，外部资料或验证尚未取得；
- 用户决定暂停或搁置某一方向。

不要为了“深度”无止境追问，也不要用已知缺口尚未解决的方案冒充完成稿。结束时简要报告确认内容、未决项、实际更新文件、正文是否同步和下一步。
